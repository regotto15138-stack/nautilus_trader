# CHANGE_REQUESTS — 变更请求与歧义登记

> 需求范围、验收口径、规格语义的任何改动，都先落在这里，再动代码。
> 目的是让"为什么会变成这样"有记录，而不是散落在对话里。

## 1. CR 何时需要

| 情况 | 是否需要 CR |
| --- | --- |
| 在既有 REQ 范围内拆任务 | 否 |
| 扩大/缩小 REQ 范围 | 是 |
| 修改验收口径 | 是 |
| 修改规格未定义的行为 | 是（先登记歧义） |
| 纯实现细节（命名、内部结构） | 否 |

## 2. CR 流程

1. 提出：写清背景、现状、拟变更、影响面、替代方案。
2. 影响评估：涉及哪些 REQ / 任务 / 接口 / 测试 / 文档。
3. 决策：由用户拍板；Agent 只给建议，不替用户决定。
4. 落地：更新 `REQUIREMENTS.md`（或歧义登记表）→ 拆任务 → 实现 → 验收。
5. 记录：`development/DECISIONS.md` 追加决策行，`CHANGELOG.md` 追加变更。

## 5. 规格歧义登记表

> 规格没定义清楚的地方，**不猜**。登记在这里，代码里保留接口与 `SPEC_AMBIGUITY` 标记。

| ID | 位置 | 歧义内容 | 当前处理 | 影响 |
| --- | --- | --- | --- | --- |
| AMB-001 | 指标 | 规格只定义 ATR14 与 SMA22，无 `ATR_MA22` | 不实现；配置含 `indicators.atr_ma_period` 即加载失败；前端显示 `N/A / SPEC_AMBIGUITY` | 研究指标缺失 |
| AMB-002 | N 结构 | 结构失效判定用哪一根 ATR、判定时点未定义 | 只保留 `NStructureDetector.structural_break_price(atr)` 接口，`invalidation_enabled=False` | PB-12、PB-13 为 `BLOCKED_BY_SPEC_AMBIGUITY` |
| AMB-003 | Zone | 最小半宽与最大存续期的取值口径 | 两参数进配置（`zone_min_half_width_ticks`、`zone_max_age_weeks`）并写入冻结快照 | 参数漂移会影响比对 |
