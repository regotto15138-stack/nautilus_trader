## 0. 权威来源与不变量

- 需求权威来源：`<REQUIREMENTS_PATH>`；验收：`<ACCEPTANCE_PATH>`。
- 任务状态唯一来源：`<TASK_LEDGER_PATH>`。其他索引/聊天/计划不得维护冲突状态。
- 项目上下文：`<PROJECT_CONTEXT_PATH>`；架构/接口：`<ARCHITECTURE_AND_CONTRACT_PATHS>`。
- Git 根目录与提交规则：`<GIT_TOPOLOGY_AND_COMMIT_RULE>`；未获明确授权不提交/推送、不做破坏性 Git 操作。
- 未登记的任务不进行正式修改；未验证的工作不标完成；用户已有改动不可覆盖。

## 1. 每个 Session 启动协议

1. 读取本文件、项目上下文和适用的上游/安全/贡献规范。
2. 读取唯一任务状态源，核对当前 TASK、状态、负责人、依赖和授权路径。
3. 阅读当前任务契约与必要上下文文件；从 L0 项目约束/状态、L1 模块接口、L2 任务/相关源码、L3 执行结果逐层按需加载。
4. 核对 Git 状态、分支/最近提交和未提交差异；读取未完成交接，核实而非盲信其描述。
5. 若无任务或任务未达到可开工状态，先澄清、登记来源/目标/范围/验收/验证/风险，不得先改文件。

## 2. 任务与执行

- 任务必须有来源、目标、输入/输出、文件范围、依赖、可验证验收条件、验证命令和失败/回滚风险。
- 开工前将任务状态更新为 `<IN_PROGRESS_STATE>` 并记录 owner；只改显式授权范围。若要越界或接口设计冲突，先停下申请批准并更新契约。
- 同一文件单写者；并行任务需依赖兼容且路径互斥。角色分工按最小必要原则，不为形式启动多 Agent。
- 修改前读既有实现与模式；最小变更，不做无关重构，不引入未经批准依赖。
- 测试不得被删除/弱化以制造通过；报告区分通过、失败、跳过、未运行。

## 3. 质量、Git 与验收

- 按项目定义的代码风格、精确数值、时间/并发、安全和兼容性约束执行：`<PROJECT_SPECIFIC_RULES>`。
- 逐项检查需求、架构、正确性/边界、安全、自动化测试、Diff/范围和文档同步。
- 记录命令及实际输出摘要；测试未执行不算通过。缺陷等级与阻断规则：`<SEVERITY_POLICY>`。
- `IMPLEMENTED` 不等于 `ACCEPTED`；只有独立审查、验证证据与最终验收均满足，才能标为接受。
- 提交信息和 stage 范围遵循 `<REPOSITORY_COMMIT_RULES>`；未经用户明确要求不执行提交或远程操作。

## 4. 上下文预算与交接

- 按当前可用预算控制探索；减少重复读取和无关输出，不以节省 token 损害正确性。任何百分比阈值仅为项目管理策略，除非平台明确提供，否则不是硬限制。
- Session 结束/切换/阻塞时更新唯一状态源；按需增量更新项目快照并填写 `<HANDOFF_PATH>`。
- 交接记录未完成任务、Git 改动归属、验证缺口、风险、下一步和所需上下文入口；不清理或重置用户工作。

## 5. 开发复盘

开发复盘记录"方法约束"，会话交接记录"现状"，两者不互相替代。只有写进规则文件（本文件、项目配置或任务 notes）的复盘才算生效，聊天里写的不算。

- 触发条件（由项目裁剪，示例）：出现需退修的缺陷或返工；同一文件在同一 Session 被读 5 次以上；中途切换模型/推理强度/执行器或出现限流报错；接近预算或交接阈值；任务被审查退回。
- 内容按顺序写：现象（可核对的事实）→ 根因（继续追问"为什么会这样"）→ 是规则缺口还是执行失误 → 下次可执行的动作 → 生效位置。
- 规则文件只增不删；新规则与旧规则冲突时改写旧规则并注明替代关系，同一规则只写一处，别处只引用。
- 涉及 token 消耗时，必须区分"可见上下文"与"请求级用量"，给出请求数、缓存未命中次数与全价输入合计；只有聊天观感的结论不算复盘。

## 6. 沟通与未决事项

- 面向用户使用项目约定语言，简洁报告变更、证据、未完成项和风险。
- 不确定、规格缺失、权限不足或需要人类价值判断时，明确说明并提出可选项；未经授权不代替人类裁决。
