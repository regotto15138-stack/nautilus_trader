稳定的工程开发机制：
1. 需求有来源：所有代码修改都能追溯到需求。
2. 任务可执行：需求拆分成有明确输入、输出和验收标准的 TASK。
3. 上下文隔离：主 Agent 不承担所有代码阅读工作，子 Agent 不加载无关项目背景。
4. 修改可控：限制文件修改范围，避免多个 Agent 互相覆盖。
5. Token 可控：按任务分配上下文预算，控制无效读取和重复输出。
6. 质量闭环：代码实现必须经过独立审查和测试验收。
7. Session 可恢复：中断后能通过项目文件恢复工作，不依赖历史对话。

建议采用 **1 个主 Agent + N 个专项 Agent + 统一任务状态文件 + Git 变更审计** 的模式。

以下给出可以直接放进项目的规范。它不是依赖某个特定插件的配置，而是 DSH 工作流层规范；插件只负责增强执行能力，不决定项目事实和任务状态。

7. 无法确认的信息必须标记为待验证，不得推测填充。

## **2.2 自动维护触发条件**

主 Agent 在以下事件发生时检查是否需要更新：

| 触发事件       | 是否更新    |
| ---------- | ------- |
| 新模块完成      | 是       |
| 架构发生变化     | 是       |
| 核心接口变化     | 是       |
| 技术栈变化      | 是       |
| 任务状态变化     | 仅更新必要字段 |
| 普通 Bug 修复  | 通常不更新   |
| 修改局部变量     | 不更新     |
| Session 结束 | 检查后更新   |
| 新的技术决策确认   | 是       |

不要每完成一个小任务就重写整个 `PROJECT_CONTEXT.md`。

采用增量更新：

```
读取当前 PROJECT_CONTEXT
        ↓
对比任务完成前后的项目状态
        ↓
判断是否属于重要状态变化
        ↓
只修改受影响章节
        ↓
检查引用文件和任务状态
        ↓
Git Diff 审核
        ↓
保存
```

## **2.3 防止上下文文件膨胀**

制定三个限制：

- 不在 Context 里面存放完整代码。
- 不在 Context 里面存放历史任务执行过程。
- 不在 Context 里面存放完整错误日志。

错误日志保存在独立文件，Context 只记录问题摘要及路径。

例如：

```
错误：模块初始化存在循环依赖。

影响：
Module A -> Module B -> Module A

详细日志：
development/debug/INIT-001.md

状态：
待修复
```

# **三、需求文档到 TASKS 的拆分规则**

这是第二个核心。

不允许 Agent 读取需求文档后，直接开始修改代码。

必须先建立：

**需求 → 功能点 → 技术任务 → 依赖关系 → 验收标准**

## **3.1 需求分解流程**

```
REQUIREMENTS.md
       |
       v
需求识别
       |
       v
功能点拆分
       |
       v
技术方案分析
       |
       v
模块依赖分析
       |
       v
TASK 生成
       |
       v
任务评审
       |
       v
进入开发
```

每条需求必须分配唯一 ID：

```
REQ-001
REQ-002
REQ-003
```

每个技术任务必须分配唯一 ID：

```
TASK-001
TASK-002
TASK-003
```

需求和任务必须建立关联。

例如：

```
REQ-001
 ├── TASK-001
 ├── TASK-002
 └── TASK-003
```

## **3.2 TASK 拆分粒度**

一个 TASK 应满足：

1. 有明确的开发目标。
2. 有明确的输入和输出。
3. 有明确的代码修改范围。
4. 可以独立验证。
5. 有明确的完成条件。
6. 不依赖大量隐含上下文。

建议一个 TASK 对应一个相对独立的工程交付。

例如，不能这样拆：

```
TASK-001：实现整个交易系统。
```

应该这样拆：

```
TASK-001：实现 Bar 数据模型。
TASK-002：实现时间周期转换。
TASK-003：实现 ZigZag Swing 识别。
TASK-004：实现 Swing 状态管理。
TASK-005：实现 N 结构识别。
TASK-006：实现结构失效判定。
```

## **3.3 TASK 优先级**

| 优先级 | 定义             |
| --- | -------------- |
| P0  | 阻塞其他任务或涉及核心正确性 |
| P1  | 当前里程碑必须完成      |
| P2  | 重要增强功能         |
| P3  | 优化、重构和非关键功能    |

## **3.4 TASK 状态机**

```
DRAFT
  |
  v
READY
  |
  v
IN_PROGRESS
  |
  v
IMPLEMENTED
  |
  v
REVIEWING
  |
  v
TESTING
  |
  v
ACCEPTED
```

异常状态：

```
BLOCKED
REJECTED
CANCELLED
```

规则：

- `DRAFT`：任务定义尚未通过评审。
- `READY`：输入、范围和验收条件已经明确。
- `IN_PROGRESS`：允许开始修改代码。
- `IMPLEMENTED`：代码实现完成，但尚未验收。
- `REVIEWING`：等待独立代码审查。
- `TESTING`：进入测试验证。
- `ACCEPTED`：全部验收条件通过。
- `BLOCKED`：存在无法继续的依赖或外部阻塞。
- `REJECTED`：审查或测试不通过，需要修复。
- `CANCELLED`：任务被正式取消。

不能因为 Agent 声称完成，就直接将任务标记为 `ACCEPTED`。

## **3.6 任务拆分的质量门槛**

主 Agent 必须检查：

| 检查项   | 通过条件                      |
| ----- | ------------------------- |
| 需求可追溯 | 每个 TASK 都有需求来源，或有明确的技术债来源 |
| 任务完整  | 有输入、输出、范围和验收标准            |
| 任务独立  | 不存在不必要的交叉修改               |
| 依赖明确  | 有向无环依赖图，循环依赖必须解决          |
| 测试明确  | 知道如何证明任务完成                |
| 风险明确  | 识别接口、并发、数据一致性等风险          |

不满足以上条件的任务不能进入 `READY`。

# **四、主 Agent 和子 Agent 的上下文隔离**

这是大型项目最容易浪费 Token 的地方。

核心原则：

**主 Agent 管理全局知识，子 Agent 只获取完成当前任务所需的局部知识。**

## **4.1 Agent 职责定义**

| Agent     | 职责            | 是否读取全局 Context | 是否修改代码  |
| --------- | ------------- | -------------- | ------- |
| Main      | 架构、任务分配、调度、验收 | 是              | 原则上否    |
| Analyst   | 需求分析、任务拆分     | 按需             | 否       |
| Architect | 架构和接口设计       | 是，精简版          | 否       |
| Developer | 具体功能实现        | 否，只读任务上下文      | 是       |
| Reviewer  | 独立代码审查        | 按需             | 默认否     |
| Tester    | 测试和回归验证       | 否，只读测试上下文      | 测试代码可修改 |

不需要每个任务都启动六个 Agent。

例如，一个简单 Bug 修复：

```
Main → Developer → Reviewer → Main
```

一个复杂模块开发：

```
Main
 ├── Analyst
 ├── Architect
 ├── Developer-A
 ├── Developer-B
 ├── Reviewer
 └── Tester
```

## **4.2 上下文分层**

建议采用四层上下文结构：

**L0：项目全局上下文**

PROJECT_CONTEXT.md · AGENTS.md

所有 Agent 都需要遵守的全局约束，但不要求每个子 Agent 完整读取所有项目背景。

**L1：模块上下文**

MODULES.md · API_CONTRACTS.md

只提供当前模块的架构、接口、依赖和设计约束。

**L2：任务上下文**

TASK-001.md · 当前相关源文件

子 Agent 实际执行任务所需要的全部信息。

**L3：执行上下文**

工具输出 · 测试结果 · Git Diff

只在任务执行过程中动态加载。

### **子 Agent 的读取规则**

Developer Agent 启动时：

1. 接收 `AGENTS.md` 中的必要执行约束。
2. 接收任务专属输入。
3. 读取当前模块的接口定义。
4. 根据需要读取相关源文件。
5. 不主动读取其他模块的完整实现。
6. 遇到缺失依赖时，向主 Agent 申请补充上下文。

不允许：

```
Developer 启动
    ↓
读取整个 PROJECT_CONTEXT
    ↓
读取全部 ARCHITECTURE
    ↓
读取全部 REQUIREMENTS
    ↓
遍历整个 src
    ↓
开始开发
```

这属于低效上下文加载。

## **4.3 上下文隔离的一个关键细节**

上下文隔离不代表子 Agent 可以不知道项目约束。

例如，开发 ZigZag 模块的 Agent，不需要了解交易系统全部策略，但必须知道：

- Bar 数据模型。
- 时间周期定义。
- Swing 的生命周期。
- 指标状态更新规则。
- 历史数据回放要求。
- 线程安全和事件处理约束（如果适用）。

所以应该提供一个精简的 `MODULE_CONTEXT.md`：

```
# MODULE_CONTEXT

## 模块
ZigZag

## 职责
从 Bar 数据中识别 Swing 高低点。

## 上游依赖
Bar
Instrument
Timeframe

## 下游依赖
NStructure
TrendAnalyzer
ZoneDetector

## 核心接口
- update(bar)
- swings()
- reset()

## 关键约束
- 历史回放结果必须确定。
- 相同输入序列必须得到相同结果。
- 未确认 Swing 不得作为已确认结构输出。
- 不允许修改 Bar 基础数据模型。

## 相关文件
- src/indicators/zigzag.py
- src/models/swing.py
- tests/indicators/test_zigzag.py
```

这样就能实现有针对性的上下文传递。

# **五、子 Agent 输入输出协议**

主 Agent 和子 Agent 之间不能仅依赖自然语言对话。

必须建立结构化任务协议。

这样做有两个好处：

- 减少子 Agent 对任务的误解。
- 主 Agent 不需要重新阅读子 Agent 的全部推理过程。

## **5.1 输入协议**

每个子 Agent 必须收到以下信息：

| 字段               | 必须 | 说明       |
| ---------------- | -- | -------- |
| task_id          | 是  | 唯一任务 ID  |
| role             | 是  | Agent 职责 |
| objective        | 是  | 任务目标     |
| requirement_refs | 是  | 需求依据     |
| context_files    | 是  | 指定上下文    |
| allowed_paths    | 是  | 可修改范围    |
| forbidden_paths  | 是  | 禁止修改范围   |
| interfaces       | 是  | 接口约束     |
| dependencies     | 是  | 前置依赖     |
| acceptance       | 是  | 验收标准     |
| token_budget     | 是  | Token 预算 |
| output_format    | 是  | 输出格式     |

以下是实际传递的任务示例：

```

{
  "task_id": "TASK-003",
  "role": "developer",
  "objective": "实现 ZigZag Swing 确认逻辑",
  "requirement_refs": [
    "REQ-012"
  ],
  "context_files": [
    "AGENTS.md",
    "docs/MODULES.md",
    "docs/API_CONTRACTS.md",
    "development/tasks/TASK-003.md",
    "src/models/bar.py",
    "src/models/swing.py"
  ],
  "allowed_paths": [
    "src/indicators/zigzag.py",
    "tests/indicators/test_zigzag.py"
  ],
  "forbidden_paths": [
    "src/models/bar.py",
    "src/strategy/",
    "src/execution/"
  ],
  "interfaces": [
    "update(bar)",
    "swings()",
    "reset()"
  ],
  "dependencies": [
    "TASK-001",
    "TASK-002"
  ],
  "acceptance": [
    "Swing 高低点识别正确",
    "确认状态符合定义",
    "历史回放结果确定",

  ],

## **5.3 子 Agent 异常处理协议**

必须定义以下情况：

| 情况         | 子 Agent 行为                |
| ---------- | ------------------------- |
| 需求不明确      | 返回 CLARIFICATION_REQUIRED |
| 缺少接口定义     | 返回 BLOCKED                |
| 超出修改范围     | 停止修改并申请授权                 |
| 测试失败       | 返回 FAILED                 |
| 发现架构冲突     | 返回 DESIGN_CONFLICT        |
| Token 预算不足 | 保存当前状态并返回 CONTEXT_LIMIT   |
| 发现其他模块 Bug | 记录问题，不擅自修改                |

尤其要避免子 Agent 自行扩大任务范围。

例如，开发者发现 Bar 模型设计不合理时，不能直接修改 Bar 模型，必须向主 Agent 提出变更申请。

# **六、文件读取和代码修改权限边界**

大型项目必须有权限约束，否则多 Agent 并行开发容易出现文件覆盖和架构漂移。

建议采用三级权限。

## **6.1 文件权限模型**

| 权限    | 含义               | 适用 Agent   |
| ----- | ---------------- | ---------- |
| READ  | 可以读取             | 所有相关 Agent |
| WRITE | 可以修改指定文件         | Developer  |
| ADMIN | 可以修改全局规范、架构和任务定义 | Main       |

具体划分：

| 文件              | Main | Analyst | Architect | Developer | Reviewer | Tester  |
| --------------- | ---- | ------- | --------- | --------- | -------- | ------- |
| PROJECT_CONTEXT | RW   | R       | R         | R         | R        | R       |
| AGENTS.md       | RW   | R       | R         | R         | R        | R       |
| REQUIREMENTS    | RW   | R       | R         | R         | R        | R       |
| ARCHITECTURE    | RW   | R       | RW        | R         | R        | R       |
| TASKS           | RW   | R       | R         | R         | R        | R       |
| TASK 文件         | RW   | R       | R         | R         | R        | R       |
| src             | R    | R       | R         | 指定范围 RW   | R        | R       |
| tests           | R    | R       | R         | 指定范围 RW   | R        | 指定范围 RW |
| REVIEW 文件       | R    | R       | R         | R         | RW       | R       |
| SESSION_HANDOFF | RW   | R       | R         | R         | R        | R       |

说明：

- `R` = Read。
- `W` = Write。
- `RW` = Read + Write。

实际执行时，权限必须通过 DSH 可用的工具授权、工作区隔离或文件系统权限落实，不能只依靠 Prompt。

## **6.2 代码修改边界**

Developer 每次执行任务前必须确认：

```
当前任务：
TASK-003

允许修改：
src/indicators/zigzag.py
tests/indicators/test_zigzag.py

禁止修改：
src/models/bar.py
src/strategy/
src/execution/

如果需要修改禁止区域：
停止任务
→ 提交修改申请
→ 主 Agent 审批
→ 更新任务范围
→ 继续开发
```

## **6.3 并发修改规则**

必须建立文件级锁定机制。

例如：

```
TASK-001 → src/models/bar.py
TASK-002 → src/indicators/zigzag.py
TASK-003 → src/strategy/trend.py
```

三个任务可以并行执行。

但是：

```
TASK-001 → src/models/bar.py
TASK-002 → src/models/bar.py
```

不能默认并行修改。

建议规则：

1. 同一文件同一时间只能有一个写入 Agent。
2. 不同 Agent 不共享未提交的工作区修改。
3. 子 Agent 完成后提交独立 Git 分支或独立工作区的变更。
4. 主 Agent 检查 Diff 后合并。
5. 接口变更必须经过架构确认。
6. 合并后运行相关回归测试。

如果 DSH 不支持原生文件锁，使用 Git Worktree 或独立工作目录隔离，而不是让多个 Agent 直接共用一个工作区。

## **6.4 修改前后强制检查**

修改前：

```
git status --short
git branch --show-current
git diff --stat
```

修改后：

```
git status --short
git diff --check
git diff --stat
git diff
```

禁止覆盖用户已有的未提交修改。

发现与当前任务无关的 Diff 时，先识别来源，不得擅自清理或重置。

# **七、Token 使用预算管理**

这里不建议单纯追求每轮请求 Token 最少，而是控制每项任务的总 Token 消耗。

因为过度压缩会导致：

- Agent 遗漏架构约束。
- 反复读取已经读取过的文件。
- 修改后发现接口不兼容。
- 因缺失上下文反复询问主 Agent。
- 代码质量下降，后续修复成本上升。

因此采用三级预算：

1. Session 预算。
2. Agent 预算。
3. TASK 预算。

## **7.1 Token 分配策略**

下面以一个 100,000 Token 的开发 Session 预算为例：

示例 Session 总预算 100,000 Tokens

Developer

Reviewer

Tester

上下文及交接

主 Agent

预留

| 用途        | 预算      | 比例   |
| --------- | ------- | ---- |
| 主 Agent   | 18,000  | 18%  |
| Developer | 35,000  | 35%  |
| Reviewer  | 15,000  | 15%  |
| Tester    | 15,000  | 15%  |
| 上下文及交接    | 10,000  | 10%  |
| 预留        | 7,000   | 7%   |
| 合计        | 100,000 | 100% |

这是规划预算，不是 DSH 的硬限制。实际统计应区分输入 Token、输出 Token、缓存 Token，以及不同模型的计费口径。

## **7.2 不同任务的预算**

| 任务类型      | 建议总预算   |
| --------- | ------- |
| 简单 Bug 修复 | 5K～10K  |
| 普通功能开发    | 10K～20K |
| 复杂模块开发    | 20K～40K |
| 架构设计      | 15K～30K |
| 独立代码审查    | 8K～15K  |
| 跨模块重构     | 30K～60K |

这些数值是初始规划值。完成 10～20 个实际任务后，应该根据成本和质量数据校准。

## **7.3 Token 消耗分级**

建议每个 Agent 都有预算预警：

## **Token 预算状态**

**正常**

0～60%

正常开发，优先保证实现质量。

**预警**

60%～80%

停止无关探索，减少重复读取，准备交接。

**临界**

80%～95%

只允许完成当前最小闭环，禁止扩展任务。

**停止**

95%～100%

停止非必要调用，生成交接记录，转入新 Session。

注意：百分比应该以当前任务或 Session 的可用预算为分母，而不是整个模型的最大上下文窗口。

## **7.4 降低 Token 消耗的具体规则**

**文件读取**

- 先搜索符号、类名和函数名。
- 再读取命中的代码范围。
- 只有涉及整体架构时才读取完整文件。
- 不重复读取本轮已经完整获取且未发生变化的文件。

**工具输出**

- 默认只返回错误摘要和必要上下文。
- 日志先过滤，再交给模型。
- 测试失败只提供失败用例、堆栈和相关代码。
- 不要将完整构建日志直接输入主 Agent。

**代码输出**

- 不重复输出整个文件。
- 只返回变更摘要和 Diff。
- 不要要求子 Agent 描述完整推理过程。
- 优先让 Git 和测试工具提供客观证据。

**多 Agent**

- 子 Agent 不读取其他子 Agent 的完整对话。
- 主 Agent 只读取结构化交付报告。
- 接口契约通过文件传递，不通过冗长自然语言反复传递。
- 不允许多个 Agent 重复执行相同的代码探索。

## **7.5 一个重要的成本优化**

不要让 Reviewer 重新阅读整个项目。

正确流程：

```
Developer 完成代码
        ↓
Git Diff
        ↓
Reviewer 读取 Diff
        ↓
读取必要的接口和调用上下文
        ↓
发现问题时扩大读取范围
        ↓
输出审查报告
```

这比让 Reviewer 从零理解整个项目更加经济。

# **八、代码审查与测试验收流程**

必须把代码完成和任务完成区分开。

`IMPLEMENTED` 不等于 `ACCEPTED`。

建议设置五道质量门禁。

## **8.1 五道质量门禁**

1. **Gate 1：需求一致性**
    - 是否覆盖原始需求？
    - 是否存在遗漏？
    - 是否擅自增加需求？
    - 是否符合验收条件？
2. **Gate 2：架构一致性**
    - 是否遵守模块职责？
    - 是否违反依赖方向？
    - 是否破坏公共接口？
    - 是否产生循环依赖？
3. **Gate 3：代码质量**
    - 是否存在边界条件错误？
    - 是否存在资源泄漏？
    - 是否存在并发安全问题？
    - 是否有重复实现？
    - 错误处理是否完整？
4. **Gate 4：自动化测试**
    - 单元测试。
    - 集成测试。
    - 边界测试。
    - 回归测试。
    - 必要的性能测试。
5. **Gate 5：最终验收**
    - 需求覆盖率。
    - 代码变更范围。
    - 测试证据。
    - 审查结论。
    - 遗留问题。

## **8.2 代码审查必须独立**

Reviewer 不应该直接相信 Developer 的完成报告。

Reviewer 应独立检查：

1. 原始需求。
2. TASK 验收条件。
3. Git Diff。
4. 相关接口。
5. 测试结果。

重点关注以下缺陷：

| 缺陷类别 | 审查内容             |
| ---- | ---------------- |
| 逻辑错误 | 条件判断、状态转换、边界处理   |
| 架构错误 | 模块职责、依赖关系、循环依赖   |
| 数据错误 | 数据一致性、数据丢失、状态污染  |
| 并发错误 | 竞态、死锁、共享状态       |
| 性能问题 | 不必要的循环、重复计算、内存膨胀 |
| 安全问题 | 权限、输入校验、敏感信息     |
| 兼容性  | API、数据格式、历史行为    |
| 可测试性 | 是否可以稳定复现和验证      |

## **8.3 缺陷等级**

| 等级 | 定义                  | 处理      |
| -- | ------------------- | ------- |
| P0 | 数据丢失、严重安全问题、核心功能不可用 | 必须阻断    |
| P1 | 核心逻辑错误、重大架构问题       | 必须修复    |
| P2 | 一般功能错误、明显性能问题       | 验收前修复   |
| P3 | 非关键优化和代码风格          | 可记录后续处理 |

P0、P1 不允许带缺陷验收。

P2 原则上应修复；确需延期时，必须明确记录风险、影响范围和责任任务。P3 可以进入技术债清单。

## **8.4 测试策略**

采用分层测试：

```
             验收测试
                 |
           集成测试
                 |
           模块测试
                 |
           单元测试
                 |
           静态检查
```

不同任务使用不同测试范围：

| 修改内容   | 必须执行        |
| ------ | ----------- |
| 单个函数   | 单元测试        |
| 模块内部逻辑 | 单元 + 模块测试   |
| 模块接口   | 模块 + 集成测试   |
| 核心数据模型 | 全部相关模块回归    |
| 并发机制   | 并发测试 + 压力测试 |
| 存储机制   | 一致性 + 恢复测试  |
| 核心架构   | 全量回归测试      |

例如，如果你在 NautilusTrader 项目中修改 ZigZag 的 Swing 确认逻辑，不能只检查编译是否通过，还要验证：

- 相同历史 Bar 输入是否得到确定的 Swing 序列。
- 未确认 Swing 是否被错误地提前发布。
- 历史回放和实时更新是否一致。
- Swing 状态重置后是否残留旧状态。
- 多周期数据是否发生错误混用。

## **8.5 最终验收标准**

只有全部满足以下条件才能进入 `ACCEPTED`：

```
[✓] 需求已覆盖
[✓] 接口符合约定
[✓] 修改范围符合授权
[✓] 代码审查通过
[✓] 必要测试全部通过
[✓] 没有未处理的 P0/P1
[✓] Git Diff 已审核
[✓] 测试证据已保存
[✓] 文档已同步
[✓] 遗留问题已记录
```

测试未执行不能标记为测试通过。

有一个重要步骤：**必须核对 Git 状态，而不能直接相信上一 Session 的交接摘要。**

例如，上一 Session 声称任务已经完成，但 Git Diff 中仍然有未提交修改，那么新 Session 应先确认这些修改的归属，再继续开发。

最终向用户返回：
- 本次完成内容
- 未完成内容
- 测试结果
- Git 状态
- 下一 Session 的第一步操作
```

# **十、主 Agent 的总控规则（AGENTS.md）**

前面八项规范必须最终落实到主 Agent 的执行指令。

建议把下面内容作为项目根目录的 `AGENTS.md`。

```
***

### DSH 项目开发规则

#### 1. 核心原则
你是负责项目层级协调的主代理（Main Agent）。
请遵循以下原则：
1. **需求**是事实的唯一来源。
2. **架构文档**定义了技术约束。
3. **TASK 文件**定义了实现范围。
4. **Git Diff** 是代码变更的事实来源。
5. **测试**提供验证证据。
6. **会话交接文件**保持开发的连续性。

**切勿**在未经验证的情况下假设任务已完成。

#### 2. 启动协议
在每个会话（Session）开始时：
1. 阅读 `AGENTS.md`。
2. 阅读 `PROJECT_CONTEXT.md`。
3. 阅读 `SESSION_HANDOFF.md`。
4. 阅读 `development/TASKS.md`。
5. 检查当前的 Git 分支和状态。
6. 验证项目的实际状态。
7. 确定下一个可执行的任务。

**不要**重新加载整个项目历史。

#### 3. 需求管理
在实现之前：
1. 分析原始需求。
2. 识别功能性和非功能性需求。
3. 创建需求 ID。
4. 将需求拆分为可独立验证的任务。
5. 识别依赖关系。
6. 定义验收标准。
7. 拒绝不完整或未就绪的任务。

只有状态为 **READY** 的任务才能进入实现阶段。

#### 4. 代理编排
**主代理 (Main Agent)：**
*   拥有全局上下文。
*   负责任务调度。
*   负责架构协调。
*   负责最终验收。

**子代理 (Sub Agents)：**
*   接收明确的任务契约。
*   仅接收必要的上下文。
*   遵循分配的文件权限。
*   返回结构化报告。
*   **未经批准，绝不**扩大任务范围。

仅当任务具有独立的写入范围且依赖关系兼容时，才允许并行执行。

#### 5. 上下文管理
使用四个上下文层级：
*   **L0:** 全局项目上下文。
*   **L1:** 模块上下文。
*   **L2:** 任务上下文。
*   **L3:** 执行上下文。

**不要**加载不必要的文件。
**不要**重复读取未变更的文件。
当摘要或针对性摘录已足够时，**不要**发送完整的日志或源文件。

#### 6. 文件权限
在每次代码修改之前：
1. 检查 `allowed_paths`（允许路径）。
2. 检查 `forbidden_paths`（禁止路径）。
3. 检查现有的 Git 修改。
4. 验证没有冲突的写入者。
5. 记录变更。

任何超出授权范围的修改都需要审批。
**切勿**覆盖无关的用户更改。

#### 7. Token 预算
每个任务必须定义 Token 预算。
*   **达到 60% 时：** 减少不必要的探索。
*   **达到 80% 时：** 停止范围扩展，准备任务交接。
*   **达到 95% 时：** 停止非必要工作，保存当前状态，生成交接文档。

**不要**为了节省 Token 而牺牲正确性。

#### 8. 实现协议
对于每个任务：
1. 理解任务。
2. 检查相关接口。
3. 确认实现边界。
4. 实现最小的完整解决方案。
5. 运行相关测试。
6. 审查 Git Diff。
7. 提交结构化输出。

**不要**重构无关的模块。

#### 9. 审查协议
每个非平凡的实现都必须经过独立审查。
检查项：
*   需求符合性。
*   架构符合性。
*   正确性。
*   边界条件。
*   错误处理。
*   并发性。
*   性能。
*   兼容性。
*   测试覆盖率。

P0 和 P1 级缺陷将阻碍验收。

#### 10. 验收协议
任务只有在满足以下条件时才能变为 **ACCEPTED**（已验收）：
*   实现已完成。
*   范围受控。
*   审查已通过。
*   要求的测试已通过。
*   证据已记录。
*   剩余风险已记录。

**IMPLEMENTED**（已实现）并不等于 **ACCEPTED**（已验收）。

#### 11. 会话交接
在结束会话之前：
1. 更新任务状态。
2. 检查 Git 状态。
3. 记录未提交的更改。
4. 如有必要，更新项目上下文。
5. 生成 `SESSION_HANDOFF.md`。
6. 记录下一步执行步骤。

**切勿**声称未经验证的工作已完成。

#### 12. 沟通
优先使用简洁、结构化的输出。
报告内容应包括：
*   改变了什么。
*   为什么改变。
*   哪些文件被改变。
*   运行了哪些测试。
*   哪些通过或失败。
*   哪些问题仍未解决。

**不要**返回冗长的内部推理过程。

***
```

# **十一、如何在 DSH 中落地**

不要一次性把所有规则塞进 DSH 的全局配置。

分三层实施：

| 层级 | 配置位置          | 内容              |
| -- | ------------- | --------------- |
| 全局 | DSH Agent 指令  | 基本行为、Token 节约原则 |
| 项目 | `AGENTS.md`   | 项目开发规范          |
| 任务 | `TASK-xxx.md` | 任务输入、权限和预算      |

这样可以避免：

- 每个项目加载不相关的开发规则。
- 每个子 Agent 重复读取所有规范。
- 全局 Prompt 过长。
- 项目规则与 DSH 本身的工具配置混在一起。

**自动化程度建议：**

| 工作          | 自动化策略           |
| ----------- | --------------- |
| 读取项目上下文     | 自动              |
| TASK 状态更新   | 自动生成，主 Agent 确认 |
| Agent 任务分发  | 自动              |
| 文件范围检查      | 自动化拦截           |
| Token 统计    | 自动              |
| Git Diff 检查 | 自动              |
| 单元测试        | 自动              |
| 代码审查        | 自动执行，主 Agent 验收 |
| 架构修改        | 人工批准            |
| 破坏性操作       | 人工批准            |
| Session 交接  | 自动生成            |

注意，Prompt 中的权限声明本身不能构成真正的文件访问控制。必须结合 DSH 工具权限、独立工作区、Git Worktree 或文件系统权限实施。

# **十二、实施优先级**

不要一次性开发完整的自动化系统。建议分四个阶段。

1. **P0：建立项目管理基础**

   第一阶段
    - 创建目录结构
    - 创建 AGENTS.md
    - 创建 PROJECT_CONTEXT.md
    - 创建 TASKS.md
    - 创建 SESSION_HANDOFF.md
    - 建立 TASK 状态机

   验收：一个 Session 能独立完成一个 TASK，并正确记录状态。
2. **P1：实现 Agent 协作机制**
    - 定义 Agent 角色
    - 定义输入输出协议
    - 建立任务依赖图
    - 建立文件修改范围
    - 实现独立审查流程

   验收：两个 Developer 可以安全并行开发不同模块。
3. **P2：实现 Token 优化机制**
    - Token 预算管理
    - 工具输出压缩
    - 上下文分层读取
    - 重复文件读取控制
    - Session 自动交接

   验收：跨 Session 开发不需要重新加载全部历史。
4. **P3：质量闭环自动化**
    - 自动生成测试计划
    - 自动执行相关测试
    - 自动检查 Git Diff
    - 自动生成审查报告
    - 自动检查验收条件

   验收：任务从需求到 ACCEPTED 有完整证据链。

# **十三、最终架构建议**

整套系统最终形成以下工作流：

**需求文档**

REQUIREMENTS / ACCEPTANCE

**Main Agent**

上下文管理 · 需求拆分 · 任务调度 · 架构协调

**任务执行层**

**Developer**

实现

**Reviewer**

审查

**Tester**

测试

**质量门禁**

Git Diff · Review · Tests · Acceptance

**项目状态持久化**

PROJECT_CONTEXT · TASKS · DECISIONS · SESSION_HANDOFF

下一个 Session 从持久化状态继续执行

## **十四、重视的三个设计**

**1. TASK 是整个系统的调度中心。**

需求、代码修改、测试、审查和验收都必须关联 TASK ID。没有 TASK ID 的代码修改，不应直接进入正式开发流程。

**2. 上下文应该按需加载，而不是按角色固定加载。**

Developer 只读取实现需要的上下文，Reviewer 只读取审查需要的上下文。Agent 角色决定工作职责，任务决定实际读取范围。

**3. 项目文件才是长期状态的权威来源。**

Session、Agent 对话和模型记忆都是临时工作载体。只有经过验证并写入项目文件的需求、决策、任务状态和交付结果，才能成为下一 Session 的可靠依据。
