# Token 预算（Token Budget）

原则：任务预算在执行前分配，执行中按阈值降级，超预算先交接而不是硬冲。

## 1. 单任务预算（按复杂度）

| 复杂度 | 场景 | 预算（input+output） |
| --- | --- | --- |
| S | 简单修复、单文件、文档 | 5–10K |
| M | 普通功能、2–5 文件 | 10–20K |
| L | 复杂模块、跨层改动 | 20–40K |
| XL | 架构级、跨模块重构 | 30–60K |
| R | 代码审查 | 8–15K |
| A | 架构与任务拆分 | 8–15K |

## 2. Session 预算分配（示例 100K）

| 角色 | 占比 | 说明 |
| --- | --- | --- |
| Main | 18% | 拆分、审查、验收、交接 |
| Developer | 35% | 实现 + 自测 |
| Reviewer | 15% | 审查 + 独立跑测试 |
| Tester | 15% | 专项验证（如启用） |
| 上下文交接 | 10% | SESSION_HANDOFF 与恢复成本 |
| 预留 | 7% | 异常与返工 |

## 3. 阈值动作

- **60%**：停止探索性阅读，只读与当前验收直接相关的文件。
- **80%**：停止扩展功能，收敛 diff，准备交接摘要。
- **95%**：停止执行，写 SESSION_HANDOFF，交回 Main。

## 4. 上下文加载分层（避免全量读项目）

| 层 | 内容 | 何时加载 |
| --- | --- | --- |
| L0 | `AGENTS.md` + `PROJECT_CONTEXT.md` | 每个 Session 开始 |
| L1 | `docs/MODULES.md`、`docs/API_CONTRACTS.md` | 涉及模块边界时 |
| L2 | 当前 TASK + 其 `context_files` 列出的源码 | 开工时 |
| L3 | 工具输出、测试日志、Git Diff | 执行中按需，用完即弃 |

规则：
- 上述预算与阈值是项目规划/预警策略，不是 DSH 或模型必然支持的硬性限制；按当前实际预算能力判断。
- Developer 不遍历整个 `src/`；缺信息向 Main 申请补充 `context_files`。
- Reviewer 先读 Diff，再按需扩读被改文件与调用方。
- 长输出用 tail/摘要，不把完整日志塞回上下文；需要时写进证据文件路径。

## 5. 计量口径（口径不同，数字不可直接比较）

预算按**可见上下文**计（可见上下文 + 输出），成本按**请求级用量**计。两者差一个量级，不能互相替代：

- 可见上下文 = 系统提示 + 对话消息 + 工具结果，DSH 界面与压缩插件看到的就是这个数。
- 请求级用量 = 供应商每次 API 调用实际计费的输入；DSH 每一步都会重新发送完整上下文（含系统提示、工具说明与全部历史）。
- 同一段历史会在后续每一步被重复计费：250 次请求的会话，输入侧合计 1.53M token，而可见上下文峰值只有约 274K。
- 供应商侧前缀缓存只记录 `cache_read`，不抵扣本地预算：一条 250 次请求的会话，`cache_read` 可达 45M，但真正付全价的是 8 次缓存未命中的请求（合计 1.27M，占输入侧 83%）。

因此：

- 判断"某会话为何耗 token"，先看**请求级账本**（请求数 × 单次输入），不要只看上下文占用或对话条数。
- 判断"是否超预算"，用**可见上下文峰值**对第二节的 Session 预算。
- 汇报 token 使用量时写明口径（可见 / 请求级 / 含缓存读）。

## 6. 单次请求固定成本核算

每次请求都要重付一遍固定前缀。2026-11-23 实测（`session-c996353b-c0c2`，250 次请求，codex/gpt-6-luna + gpt-6-sol）：

| 组成部分 | 字节 | 占比 | 来源 / 能否按会话削减 |
| --- | ---: | ---: | --- |
| 系统提示合计 | 108.1–108.2K | 100% | 下面各行相加 |
| ├ `run_code` SDK（71 个工具的参数 + 输出 schema） | 89.4K | 83% | PTC 执行器；`selectedDefault: ptc` 时必然存在。改用 native 执行器可将此段降到约 2.5K |
| ├ AgentTeams 主理协议 | 5.2K | 5% | agent-teams 插件，整段常驻 |
| ├ PTC 使用说明与"仅能调用 tools.*"约束 | 4.7K | 4% | 随 PTC 一起出现 |
| ├ DSH 通用工具约定（batch/后台任务/web_fetch 引用等） | 2.6K | 2% | DSH 基座 |
| ├ Agency 专家模式 | 2.6K | 2% | agency 插件，未启用专家时也常驻 |
| ├ 人格内核 + 本会话状态摘要（whale-pal） | 3.1K | 3% | 随状态变长而增长 |
| ├ 专家团中文协调段 | 1.4K | 1% | agent-teams 插件 |
| └ 运行时上下文（工作目录/沙箱/技能清单等） | 2.6K | 2% | DSH 基座 |
| 原生工具 schema（`request/header.tools`） | 2.5K | — | 单个 `run_code` 入口 |

换算与方法：

- 92K 的 ts 代码块按 ASCII 计（约 1.6 字节/token，约 57K token）；其余中文/混合段落按 3 字节/token（约 5.5K token）；合计约 27K。由于供应商侧 `inputTokens` 含系统提示、工具 schema 与全部历史消息，直接按字节除算会严重低估：首请求实测 input 27,659（纯系统提示 + 首条指令），此后每请求平均 6,107，差异全部来自历史消息。
- 核算时以账面 `inputTokens` 为准，字节估算只用于判断"哪一段该削"。
- 该前缀落在**缓存前缀区**：命中时按 `cache_read` 计（便宜），但模型/路由/推理强度/工具面/系统提示任何一项变化都会让它重新全价计费。
- 核算方法：从会话日志取 `request/header` 与首条 `system/message`，按上表分段量长度；不要用"对话里看到了多少字"代替。
- 结论口径：固定前缀属于"每次请求的底价"，不能靠压缩对话消除；只能通过换执行器、关掉常驻插件段、减少请求次数来降。

## 7. 已验证有效的降耗措施

按收益排序，均为配置层改动，不依赖模型行为：

1. **混合模型路由**：探索/长上下文阶段留在便宜模型，收尾在昂贵模型上做短会话。实测同类会话在 gpt-6-sol 上 76 次请求付了 1.05M 全价输入，而 gpt-6-luna 174 次请求只付 479K。
2. **控制缓存未命中**：不要在会话中途切换模型、推理强度或工具面；每次变化都会让整段旧上下文按全价重发（实测 4 次切换造成 1.23M 全价输入）。确需切换时，切完立即压缩并收尾，不在旧上下文上继续长跑。
3. **执行器按需选**：只在需要批量工具调用时用 PTC；普通读文件/搜索会话用 native 执行器，直接省掉 87K 前缀。
4. **长任务拆会话 + 交接**：同一会话从 10:58 跑到 12:26 只用了 1 个 `/compact`，历史在约 200K 上下文上反复重发；按 60%/80%/95% 阈值交接，比事后压缩更省。
5. **减少重复读**：实测 193 次 read 只覆盖 43 个文件，75% 是同一段落的带 offset/limit 重读。需要反复核对的定位行号，写进任务证据或交接文件，而不是反复重读。
6. **工具结果裁剪**：`tool-result-pruner` 只在压缩触发时才工作，默认阈值 8192 字符。长日志、大 JSON、整份规格用 `tail`、`grep -n` 定位后局部读，不要整段进上下文。

## 8. 汇报要求

- 每个 Session 结束时在 `SESSION_HANDOFF.md` 第 13 节记录：请求数、input、cache_read、output，并标注模型与是否发生过模型/执行器切换。
- 单次请求输入超过 200K 或出现连续缓存未命中时，视为异常，先查模型/推理强度/工具面是否变化，再查是否读入了超大文件。
- 同一会话累计输入超过本节第 7 条第 4 项阈值仍未见收敛，必须先写交接再继续，不允许"再跑一轮看看"。
