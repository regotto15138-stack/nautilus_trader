# 原子任务与增量追溯规则

TASK-015 制定；状态唯一来源为 [tasks.json](tasks.json)，本文件不维护第二份状态表。

## 两个不同维度

- **原子性**：一个任务只有一个交付目标，输入、输出、非目标和写入边界明确。为同一目标同时修改实现、接口适配和测试是允许的；不以文件数或函数数判断原子性。
- **独立可验证性**：在已验收前置产物和固定夹具上，存在只判断本任务目标的命令与断言。允许依赖上游契约，不允许必须同时实现下游才能判断本任务是否完成。单元/API 通过不替代真实浏览器、人工标注或人审审批。
- 每项任务分别记录 `atomicity`、`verification`、`deliverables`、`inputs`、`non_goals`、`risk_rollback`；验收报告是实现任务的证据，不把单独报告冒充业务交付物。

## 状态与调度

- ACCEPTED 表示正式完成；IMPLEMENTED 表示产物已执行但未完成正式验收；REVIEWING 表示审查中。历史状态不因一次全量测试通过批量提升。
- 新拆任务默认 DRAFT；未完成前置验收、规格决策、接口冻结或六门槛不得下发。`blockers` 记录外部决策，`depends_on` 只记录任务边。
- `depends_on` 同时包含语义依赖与文件互斥排序；`dependency_reasons` 区分两者。相同 allowed_paths 文件必须串行。验收只依赖本阶段可存在的产物，不倒置依赖后续引擎。
- 新测试路径允许尚不存在，但必须在 `planned_new_paths` 中准确声明且包含于 allowed_paths；消费上游将创建的测试须有对应依赖。实现者先创建测试再执行指定命令。未创建/未执行不算通过。
- 人工决策/数据冻结任务必须另列 `verification.manual`，逐项核对原始授权、hash、责任人与统计定义；台账结构校验不能证明这些内容。TASK-015 独立审查曾发现路径声明漂移及结构校验冒充内容验证，禁止仅复制通用断言而不区分证据来源。

## SPEC → PLAN → TASK → TEST

- 每项使用 `traceability.spec`（权威章节路径/条款）、`traceability.plan`（三计划路径/章节）、任务 ID，以及 `verification` 中 TEST-ID、命令和断言。REQ 是语义父项，不替代 SPEC。
- `traceability` 引用内容哈希通过本轮基线保存在台账 `planning_baseline`；哈希变化只触发影响分析，不表示自动批准语义变化。
- 测试状态与任务状态分开：`planned`、`passed`、`historical`、`not_run`。历史证据须保留原日期和范围，不能改写为本轮执行。

## 增量变更

1. 业务语义变更先走 CHANGE_REQUESTS；已批准 spec 的计划同步不再发明新语义。
2. 保留既有 TASK-ID、历史 evidence 和原目标快照；调整记录追加到 `revisions`，不得删除或复用任务 ID。
3. 已 ACCEPTED 任务不重写原验收结论：新增后继任务承接差量，`supersedes`/`related_tasks` 只建追溯，不偷改完成历史。
4. 修改目标/范围/测试时追加日期、原因、旧值、新值及受影响下游，重新校验 DAG/路径互斥/引用/TEST-ID；受影响完成证据标待复核，不伪造回归通过。
5. 只改受影响计划小节，保留历史快照并明确其非当前事实。P0-E 冻结 PB-01..59 场景，按所属阶段执行；后续 PB 未执行不阻断 P1-A 编码，但阻断对应能力与完整冻结。
